# Contributing to basic-pitch-rs

Thanks for your interest in basic-pitch-rs. Bug reports, parity reports, docs
fixes and code are all welcome.

This project is a port. Its first promise is that, with default settings, it
gives the same notes, pitch bends and MIDI messages as the official Python
[Basic Pitch](https://github.com/spotify/basic-pitch). Most of this guide is
about keeping that promise.

By participating, you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Security issues go through [SECURITY.md](SECURITY.md), never through public issues.

## Ground rules

1. **Parity first.** The default pipeline reproduces spotify/basic-pitch v0.4.0,
   with the output trim of upstream main. That includes upstream quirks, such as
   the +1 bin bias of pitch bends ([spotify/basic-pitch#87](https://github.com/spotify/basic-pitch/issues/87)),
   numpy's round-half-to-even, and the order of note events. Improvements over
   upstream are welcome, but always as an opt-in option whose default keeps parity.
2. **No numerical change without a fixture.** A change that can alter any value
   reaching a note, a pitch bend or a MIDI message must come with a fixture
   generated by the Python reference that shows the expected result, or with an
   explanation of why the existing fixtures already cover it.
3. **Keep the license headers.** Files translated from the Python code of
   Basic Pitch carry a header that credits Spotify, names the original file and
   states that the file was modified (Apache License 2.0, section 4). Keep it
   when you edit such a file, and add it when you port new code from upstream.
   Code that is not derived from upstream does not need it.
4. **Small, focused pull requests.** One topic per pull request, with tests.
   Open an issue or a discussion first for large changes or new public API.

## Development setup

You need:

- Rust stable (the minimum supported version is the `rust-version` in
  [Cargo.toml](Cargo.toml)). Install it with [rustup](https://rustup.rs).
- Optional: the `wasm32-unknown-unknown` target, to check the WebAssembly build:
  `rustup target add wasm32-unknown-unknown`.
- Optional: [uv](https://docs.astral.sh/uv/), only to regenerate the parity
  fixtures. Day-to-day work does not need Python: the fixtures are committed.

Repository layout:

| Path | Content |
| --- | --- |
| `crates/basic-pitch-rs` | The library (`basic_pitch`), with the bundled model in `model/nmp.onnx`. |
| `crates/basic-pitch-cli` | The `basic-pitch-rs` command-line tool. |
| `crates/parity` | Parity tests against the Python reference (not published). |
| `tests/fixtures` | Audio inputs and reference outputs, see [tests/fixtures/README.md](tests/fixtures/README.md). |
| `reference` | The Python projects that generate the fixtures, see [reference/README.md](reference/README.md). |

## Everyday commands

These are the commands CI runs. Run them before you open a pull request.

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --all-targets                      # library and CLI
cargo test --doc
cargo test --manifest-path crates/parity/Cargo.toml --release
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features
```

The WebAssembly check of the core library (no extra flags needed: the crate
selects the `getrandom` backend for `wasm32-unknown-unknown` itself):

```sh
cargo build --manifest-path crates/basic-pitch-rs/Cargo.toml \
  --target wasm32-unknown-unknown --no-default-features --features tract,bundled-model
```

Dependency policy (licenses, advisories, duplicate crates, sources) is checked
with [cargo-deny](https://github.com/EmbarkStudios/cargo-deny):

```sh
cargo install cargo-deny --locked
cargo deny check
```

Notes on features:

- `ort` (library) needs Rust 1.92 or newer, a requirement of ort itself, and
  links an ONNX Runtime you provide (`ORT_LIB_LOCATION`). `ort-download` (library)
  and `ort` (CLI, parity) download a prebuilt ONNX Runtime at build time instead;
  `--all-features` uses that.
- `cargo hack check -p basic-pitch-rs --feature-powerset --exclude-features
  ort,ort-download` checks every other combination of the library's features, as
  the CI does.
- `soxr` (CLI) compiles and statically links libsoxr, which is
  LGPL-2.1-or-later. It is opt-in and never part of the release binaries. See
  the comment in [deny.toml](deny.toml) before changing that.

## How parity is tested

The fixtures in `tests/fixtures` are produced by the official Python package
(basic-pitch 0.4.0, and upstream main for the trim mode) running the same
`nmp.onnx` model on the CPU with onnxruntime. Every intermediate stage is saved,
so each layer of the Rust pipeline is tested on its own, with Python's input:

| Layer | Fixture | Expected match |
| --- | --- | --- |
| Audio loading and resampling to 22 050 Hz mono | `audio_22050.npy` | Close, within the resampler's tolerance |
| Windowing (padding, hop, last window) | `model_input.npy` | Exact |
| Model inference | `raw_{note,onset,contour}.npy` | About 1e-6 with tract, exact with ort on the CPU |
| Output unwrapping and trimming | `v0.4.0/{note,onset,contour}.npy`, `times.npy` | Exact |
| Note creation, from Python's posteriorgrams | `polyphonic_events`, `frame_events`, `events` in each `<config>.json` | Exact frames, pitches and bends, in the same order; amplitudes within float32 rounding |
| MIDI export | `midi` in each `<config>.json` | Same parsed messages, tick for tick |
| Note creation and MIDI on adversarial posteriorgrams | `adversarial/<case>.json` | Exact; where Python raises, Rust returns an error |

Each case is checked with eight parameter sets (`default`, `thresholds`,
`freq_range`, `multiple_bends`, `no_melodia`, `no_infer_onsets`, `no_bends`,
`tempo_90`) and two variants (`v0.4.0` and `main`).

The audio cases only reach what the model outputs on a few recordings. The
adversarial cases, generated by `reference/generate_adversarial.py`, feed
`note_creation.py` with synthetic posteriorgrams that reach its corners:
thresholds at 0 and 1, plateaus and ties, frequency bounds that become negative
numpy indices, notes longer than numpy's reduction buffer, edge keys, extreme
tempos, custom pitch bend tolerances, NaN activations and notes that
`pretty_midi` cannot write.

Note creation is compared on Python's own posteriorgrams on purpose: a value
that sits a few 1e-6 from a threshold can flip a frame, so exact equality of
notes is only meaningful when both sides start from the same numbers.
End-to-end tests, from audio to notes, are a separate layer with an explicit
tolerance.

## Regenerating the fixtures

Only regenerate fixtures when the reference changes (a new upstream version, a
new test case or a new parameter set). The generation is deterministic: running
it on an unchanged reference gives byte-identical files.

From the repository root:

```sh
cd reference

# Synthetic test signals (synth, pluck, silence, short).
uv run --locked python -I make_synth.py ../tests/fixtures/audio

# v0.4.0 variant, plus audio, windows and raw model outputs.
uv run --locked python -I generate_fixtures.py ../tests/fixtures ../tests/fixtures/audio/*.wav

# Adversarial post-processing cases (no model, no audio).
uv run --locked python -I generate_adversarial.py ../tests/fixtures/adversarial

# main variant (only what differs: unwrapping, notes and MIDI).
cd main
uv run --locked python -I ../generate_fixtures.py ../../tests/fixtures ../../tests/fixtures/audio/*.wav --variant-only
```

The first `uv run` in each directory creates its virtual environment from the
lockfile. The vocadito files are copied unmodified from the tests of
spotify/basic-pitch, so they are not regenerated. See
[reference/README.md](reference/README.md) for why the reference is pinned the
way it is.

When you add a test case or a parameter set, describe it in
[tests/fixtures/README.md](tests/fixtures/README.md) and check that the size of
the fixtures stays reasonable.

## Commit messages and changelog

- Write commit messages in the imperative mood, with a short summary line
  ("Add bend_offset to the CLI", "Fix trim of the last window").
- Add an entry under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md) for every
  user-facing change.

## Releases (maintainers)

1. Bump `version` in the workspace `Cargo.toml`, move the `[Unreleased]` entries of
   the changelog under the new version, and merge to `main`.
2. Push a tag `vX.Y.Z`: [release.yml](.github/workflows/release.yml) builds the CLI
   for every platform and attaches the archives to a draft GitHub release.
3. Review the draft and publish it: [publish.yml](.github/workflows/publish.yml)
   publishes `basic-pitch-rs`, then `basic-pitch-cli`, to crates.io through trusted
   publishing (no token in the repository).
